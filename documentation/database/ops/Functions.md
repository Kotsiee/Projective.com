# ops: Functions

## The job registry (Decision #203)

Migration [`00001650_functions_ops_scheduler.sql`](../../../supabase/migrations/00001650_functions_ops_scheduler.sql);
triggers `00001897`; grants at the end of `00002510`. Every function is `SECURITY DEFINER` with
`search_path = ''` and owned by `postgres`, the pg_cron owner. Only `ops.run_job` is executable by a
role (`service_role`); `ops` is exposed to PostgREST, so every other one is revoked from `PUBLIC`,
`anon`, `authenticated` and `service_role`. Every skip or failure raises a `WARNING` and writes an
`ops.log_entries` row (`scope = 'ops.scheduler'`, `client_id = 'scheduler:<job>:<reason>'`).

| Function                                                     | Returns   | What it does                                                                                                                                                                                                                                                             |
| :----------------------------------------------------------- | :-------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fn_log_scheduler_event(job, reason, level, message, data, once_a_day)` | `void`    | The scheduler's log: WARNING + one ops row; `once_a_day` collapses a repeating configuration skip to one row per job and reason a day.                                                                                                                                         |
| `fn_job_command(name)`                                       | `text`    | What pg_cron runs: the row's `SELECT` (sql), or `SELECT ops.fn_dispatch_http_job('<name>')` (http).                                                                                                                                                                     |
| `fn_schedule_job(name)`                                      | `boolean` | Applies one row to pg_cron (`cron.schedule` upserts by name; a disabled row is unscheduled). An invalid cron expression raises `22023`, refusing the write. A missing pg_cron (`pg_cron_unavailable`) or any other refusal (`schedule_failed`) is logged and returns `false`. Unknown name: `PJ404`. |
| `fn_unschedule_job(name)`                                    | `void`    | `cron.unschedule` when the job exists; a no-op without pg_cron.                                                                                                                                                                                                          |
| `tg_scheduled_jobs_apply()` · `fn_touch_updated_at()`        | trigger   | AFTER INSERT/UPDATE/DELETE: unschedules a deleted or renamed job and applies the row. BEFORE UPDATE: stamps `updated_at`.                                                                                                                                                  |
| `fn_dispatch_http_job(name)`                                 | `bigint`  | Reads `CRON_APP_URL` and the row's `secret_name` from `vault.decrypted_secrets`, queues `net.http_post(<origin><path>, '{}', Authorization: Bearer …, 120 s timeout)` and records it in `http_job_dispatches`; returns the request id. Missing pg_net, Vault, origin or a bearer under 32 characters → `NULL` and a once-a-day `warn` row; a pg_net refusal → an `error` row. |
| `fn_settle_http_dispatches()`                                | `integer` | Settles pending dispatches from `net._http_response` (`FOR UPDATE SKIP LOCKED`), logs every non-2xx, error or timeout (`http_failed`) and every dispatch unanswered after 7 hours (`no_response`) as `error`; returns the failure count. |
| `fn_report_failed_runs()`                                    | `integer` | Reports every failed pg_cron run of the last day (`cron.job_run_details`) as one `run_failed` error row, keyed by run id so it is reported once; returns the number newly reported. |
| `fn_watch_jobs()`                                            | `integer` | `fn_settle_http_dispatches() + fn_report_failed_runs()` — the `ops-watch-jobs` job, every 10 minutes. |
| `run_job(name)` — **`service_role`**                         | `jsonb`   | Runs one job now, enabled or not: a sql job's `SELECT` (`{job, kind, result}`, the result as jsonb) or an http job's dispatch (`{job, kind, request_id}`). Unknown name: `PJ404`. Behind `deno task cron:run` (`ScheduledJobsBackendService`).                                   |

Probe: [`supabase/probes/scheduled_jobs.sql`](../../../supabase/probes/scheduled_jobs.sql) (registration,
registry ↔ `cron.job` agreement, reschedule/disable, loud skips, the queued request and its bearer,
settlement, grants).

## The contact intake (Decision #276)

Migration [`00001655_functions_ops_contact.sql`](../../../supabase/migrations/00001655_functions_ops_contact.sql);
trigger `00001897` (`trg_contact_requests_guard`, BEFORE UPDATE); grants in `00002510` (region
`[contact]`). Every function has `search_path = ''`. Only the intake door is public: `ops` is exposed
to PostgREST, so the reference generator and the guard are revoked from every role and run only
inside the doors; Remove is a signed-in caller's, the sweep's claim the service role's.

| Function                                                           | Returns   | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| :----------------------------------------------------------------- | :-------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `submit_contact_request(intent, email, anonymous, payload, attachment_ids)` — **`anon`, `authenticated`** | `jsonb` | SECURITY DEFINER. Stamps `auth.uid()` (never for an anonymous report) and re-checks everything a direct call could forge: the intent; a payload object holding only its intent's keys (`CONTACT_PAYLOAD_KEYS`), ≤ 16 KB, with a 20–5,000-character `message` and a 1–120-character `name`; every key's value as the Zod SSOT parses it — `company` 1–160 and `referenceId` 1–200 characters, `accountEmail` an address ≤ 254, `companySize` · `budget` · `topic` · `reportType` from their closed lists (declared in the function and mirrored value for value from `CONTACT_COMPANY_SIZES` · `CONTACT_BUDGETS` · `ContactSupportTopic` (one topic per help-centre category slug, `HELP_CENTRE_CATEGORY_SLUGS`, then `other` — Decision #279) · `CONTACT_SECURITY_REPORTS`, checked by `contact.contract.test.ts`), `engagement` exactly `{slug, title, format}` with `format` one of `one_off` · `pipeline` · `session` — and the keys every request of the intent stores present (the name unless anonymous; sales' company/size/budget, support's topic, security's report type); an anonymous report is security-only with no address, name or files; anything else has a valid reply address (lower-cased). Durable ceilings per rolling hour → `PR429`: 5 per address, 10 per signed-in account, 60 named requests from guests platform-wide (so rotating addresses cannot write — or notify operators — without bound) and 30 anonymous reports platform-wide (`CONTACT_DB_CEILINGS`). Attachments only from a signed-in sender (else `42501`), at most 5, distinct, each the caller's own `files.items` row with `purpose = 'contact'`, `status = 'uploaded'`, not deleted and not already linked — the caller's rows are locked first, so a concurrent Remove or sweep either finishes before the check (the file is refused) or waits. Inserts in `backlog` (re-drawing the reference on a collision), links the files, and tells every `ops.admin_users` row through `comms.fn_notify('contact.received')` — the intent and the reference, never the message. Returns `{id, reference, intent, status, created_at}`; a malformed field is `22023` naming it. |
| `set_contact_request_status(reference, status)` — **`authenticated`** | `jsonb`   | SECURITY DEFINER. Operators only (`security.is_admin()`, else `42501`); an unknown reference is `P0002`. The guard decides legality (`23514`). Returns `{reference, status, updated_at}`.                                                                                                                                                                                                                                                                          |
| `discard_contact_attachment(file_id)` — **`authenticated`**       | `jsonb`   | SECURITY DEFINER. Remove on an unsent attachment: the caller's own contact upload (declared `target_bucket = 'contact'`, or promoted `purpose = 'contact'`), not deleted, not linked — row-locked, then soft-deleted (`deleted_at`). Returns `{id, bucket_id, storage_path}` so `ContactBackendService` deletes the bytes through the Storage API. `42501` without a session, `P0002` when it is not theirs / already sent / gone, `55006` while it is `scanning`. |
| `fn_claim_stale_contact_attachments(older_than = '6 hours', limit = 100)` — **`service_role`** | `TABLE(file_id, bucket, object_path)` | SECURITY DEFINER, `LANGUAGE sql`. The hourly sweep (`contact-attachment-sweep`): soft-deletes up to `limit` (1–1,000) contact uploads older than `older_than` (never under an hour), not deleted, linked to no request — `FOR UPDATE SKIP LOCKED`, so one a submission or a Remove holds is skipped; a row `scanning` is skipped unless its check stalled an hour ago — and answers each object for the app to delete (storage objects cannot be deleted from SQL). |
| `fn_contact_reference()`                                           | `text`    | `CT-XXXX-XXXX` from eight `extensions.gen_random_bytes`, each byte's low five bits over Crockford base32 (TypeScript twin `formatContactReference`). VOLATILE.                                                                                                                                                                                                                                                                                                      |
| `fn_guard_contact_request()`                                       | trigger   | BEFORE UPDATE, every role: refuses (`42501`) any change but `status`, except `user_id → NULL` (the account-erasure FK); refuses (`23514`) any move outside backlog → in_progress \| archived, in_progress → complete \| archived, complete → archived; stamps `updated_at`.                                                                                                                                                                                          |

Probe: [`supabase/probes/contact_requests.sql`](../../../supabase/probes/contact_requests.sql) (the
bucket and catalog row, RLS and grants, reference shape, the guest / anonymous / signed-in doors,
every shape, value and attachment refusal, a sender with no profile, operator reads of sent — and
only sent — attachments and objects, moves, the guard, Remove, the sweep, the per-address and
guest ceilings and the sweep's job row) — 81 PASS in a rolled-back run on the shared database with
the on-disk definitions spliced in.
