### 2.5 Recommended build order

The dispatch pipeline, Web Push (VAPID), APNs / FCM, transactional email with signed inbound
webhooks, and Twilio are specified provider by provider in
[`../api/EXTERNAL_PROVIDERS_AND_INFRASTRUCTURE_SPECIFICATION.md`](../api/EXTERNAL_PROVIDERS_AND_INFRASTRUCTURE_SPECIFICATION.md)
§8 (Decision #335, Proposed). This audit adds the order in which they are worth building, given what
exists:

1. **Close SEC E3 / G1 / G2 first** — a dispatcher that faithfully delivers forged notifications by
   email is worse than none.
2. **Register the comms jobs** in S5060 (queue, escalation, digests, sweep, reaper, compaction) so
   the engine that already exists runs.
3. **Email** next (EPI §8.5): transactional, mandatory money and security events only, with
   suppression consulted (N8) and bounces writing `comms.channel_suppressions`. Sign the outbound
   dispatch webhook (F1310:1141-1144 sends only a `Content-Type`) before it carries anything.
4. **Web push** (EPI §8.2) for the 50 push-routed types.
5. **SMS last** (EPI §8.6 already places Twilio in Growth), and only for security alerts and
   session-starting-now reminders: per-message cost, SIM-swap exposure, and no catalog demand today.

## 6. Strategic recommendations

### 6.1 Unified messaging — decide it, then build it as a read model

The spec sells one conversation per pair that appears identically in the inbox and in the project.
The live system has two stores, and the project half silently drops DMs. **Do not merge the
tables**: `project_messages` carries stage-room semantics (channel membership, stage scoping,
submission links) that a DM does not, and the Additive Rule protects both. Unify at the **address
and read model** instead:

```ts
/** One opaque, prefixed address for every conversation surface (Decision #88). */
type ChatRef =
	| { kind: "room"; ref: `stg-${string}` | `prj-${string}`; channel: string } // comms.project_channels
	| { kind: "thread"; ref: `cht-${string}` }; // comms.dm_threads (dm · group · service_inquiry · entity_channel)

/** MessagingBackendService — the ONE send door; dispatches to the owning table. */
sendMessage(actor: Actor, ref: ChatRef, input: SendMessageInput): Promise<ServiceResult<ChatMessage>>;
```

- A `cht-…` slug on `comms.dm_threads` (edited into T16 with its Zod type and docs) replaces the
  uuid route; `/messages/dm-<handle>` resolves the pair's thread and **303**s to its `cht-…`
  address.
- The DM send writes `dm_messages.project_id` whenever `fn_dm_protected_project` resolves one; the
  project's Private Messages group then reads `dm_threads` filtered by that project, which draws the
  same thread the inbox opens.
- One door means one Tier 1 insertion point (SEC §2.3) and one rate limiter (M23).

This needs an owner ruling because it changes addresses (#339 (f)).

**Ruled:** N1 = (f) ⭐ — adopt this section: a `cht-` ref on `dm_threads`, `dm-<handle>` answering
303, one `sendMessage(actor, ChatRef)`, `dm_messages.project_id` written, the tables not merged.
**Status:** Open → COMMS MS1 (the schema window), MS2 (the door). MS1 stores the ref in a new
column, `ref`, because `dm_threads.slug` already holds the entity-channel name (#306).

#### 6.1.1 The inbox read model (absorbed from ADC Q8, 2026-10-29)

**Evidence.**

- **N+1:** `live-queries.ts:542` makes one tail query per thread (RED D-04).
- **Single thread:** `fetchConversation` runs the full fan-out to read one thread (RED D-05).
- **The code's own advice:** its comment says a single `.in().limit()` window starves quiet threads,
  and it recommends trigger-maintained summary columns.

**Options.**

| Option                                                                                                                                                                                                        | Pros                                                                                                                             | Cons                                                                                                                                                                                                                             |
| :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A.** A definer RPC, `comms.inbox_tails(p_thread_ids uuid[], p_k int)`, using `LATERAL (… ORDER BY created_at DESC LIMIT p_k)`                                                                               | One roundtrip and no schema change. Ships this week.                                                                             | Still reads every thread to sort the inbox. The inbox itself is not keyset-paginated.                                                                                                                                            |
| **B.** **Additive** columns `dm_threads.last_message_at`, `last_message_id` and `message_count`, maintained by an `AFTER INSERT` trigger on `comms.dm_messages`, with an index on `(…, last_message_at DESC)` | The inbox becomes one indexed, keyset-paginated read. The trigger is the natural hook for ADC Q7's per-participant version bump. | A schema change. It needs approval, the Zod schema and `documentation/database/comms/` in the same change (§1), and the migration edited in place. One extra `UPDATE` per message, with hot-row contention on very busy threads. |
| **C.** A materialised view refreshed on a schedule                                                                                                                                                            | No trigger                                                                                                                       | Stale between refreshes; refresh cost grows with the table                                                                                                                                                                       |

ADC's recommendation: A now, B in the next schema window. B is additive, so it never drops or alters
existing columns, and it removes the N+1 by construction.

**Ruled:** N1 ⭐ (= #341 (h) Q8; #218 (a)) — the `inbox_tails` RPC now, then the additive summary
columns plus a trigger, in the same schema window as the `cht-` ref; not a materialised view.
**Status:** Open → COMMS MS1 (RED WP12).

### 6.2 Real-time — a server-owned stream, not a browser Supabase client

A browser `supabase-js` Realtime subscription would put a database client in an island, which root
`CLAUDE.md` §2 forbids. Two compliant options:

| Option         | How                                                                                                                                                                                                                                                | Cost                                                          | Recommendation                      |
| :------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------ | :---------------------------------- |
| ETag long-poll | `/api/messaging/conversations/:ref/since?cursor=` answers `304` until a newer message exists — the Decision #173 pattern                                                                                                                           | Trivial; one indexed query per open conversation per interval | **Ship first**                      |
| SSE            | `/api/messaging/stream` holds one connection per tab; the fat service subscribes server-side (Realtime with the service role, or `LISTEN/NOTIFY` from an `AFTER INSERT` trigger) and re-checks each event under the reader's RLS before forwarding | Connection-heavy; needs sticky routing across isolates        | When typing and presence are wanted |

Until either exists, **remove the five tables from `supabase_realtime`** (RT2600): an unused
broadcast of full message rows is attack surface (SEC E1) with no product value. Removing a
publication membership changes no schema shape, but it is a behaviour change to approve (#339 (g)).

**Ruled:** N2 = (g) ⭐ — the ETag long-poll first, SSE later; the five tables leave the publication.
**Status:** Open → COMMS MS3. The other half of ruling N2 — caches invalidated through KV version
keys bumped by the writing service, TTL as the backstop — is RED's (ADC Q7, RED D-22; the primitive
landed in O·WP10a, `7f6b43d5`); MS3 consumes it. RED D-27 (a `(created_at, id)` message cursor) is
declined by MS3 (COMMS §0 notes).

### 6.3 Notifications — the engine is built; nothing drives it

The catalog, router, preferences, quiet hours, collapse and digest builder exist and are
well-modelled. The missing pieces are operational: no scheduled jobs, no transports, no suppression
check. Follow §2.5's order. The single most valuable step after SEC E3 is registering the comms
jobs, because it turns existing code on.

**Status:** SEC E3 Fixed (`660c9658`); the jobs registered (`e18489d4`); the engine's rules fixed
(NT1, `2f9a9bb6`). Transports and suppression remain (NT2–NT5).

### 6.4 Files — one ingestion contract

Three pipelines have drifted into three acceptance policies. Define one `AdmissionPolicy` per
purpose (`library_any`, `library_media`, `contact`) in `@server/services/files`, applied by one
claim → sniff → scan → decode → promote sequence, so ClamAV (SEC §4.3) and the publication gate (SEC
§3.2) each have exactly one call site. Close the direct-write policies (SEC E8) in the same change,
or the contract governs only the doors that choose to use it.

**Status:** SEC E8 Fixed separately (`dd4206d3`); the contract is Open → T·SN2 (#339 (m)).
`ASSET_DELIVERY_ARCHITECTURE.md` §8 (#393, Proposed) adds a `sale_original` purpose with its own
whitelist on top of it.

### 6.5 Search — fix recall and scope before adding signal

In order: the visibility and definer fixes (SEC E5, E6); `ef_search` (S11), without which semantic
discovery degrades exactly as the catalogue grows; erasure (SEC G16); a scheduled embedding backfill
(S14); then a lexical relevance term (S21). The commercial reason for the order: a marketplace whose
search surfaces suspended teams or cancelled briefs, or returns an empty Teams tab at scale, loses
buyer trust faster than a missing relevance signal costs conversion.

**Status:** SEC E5 Fixed (`660c9658`, deleted `dd4206d3`) and E6 Fixed (`48c1d1a5`); S11 Open → SR1;
G16 Open → IWA; S14 Open → SR2; S21 Open (no prompt).
